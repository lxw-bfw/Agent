# 从 0 撰写模式

## 进入条件

用户只给了主题、背景、概要、平台、目标，或明确要求从 0 写一篇新稿。

## 正式调研前必须完成的事

### 1. 任务卡

至少补齐这 8 项：

- 主题：到底写什么
- 对象：写给谁
- 平台：公众号 / 小红书 / 知识星球 / PDF / 课程文档
- 目标：读者读完后得到什么
- 已知输入：用户已经给了什么
- 缺失输入：还缺什么
- 时效性：哪些内容容易变
- 必须补的调研问题：写前必须查清什么

如果受众赛道属于“技术向”，任务卡里还必须额外写清：

- 受众赛道：通用向 / 技术向
- 技术主题细分：`A / B / C / D / E / F`
- 目标技术栈：语言 / 框架 / 运行环境 / 部署方式
- 仓库 / 文档 / 源码范围
- 最小闭环和关键工程权衡是什么

如果文章类型属于“教程型”，任务卡里还必须额外写清：

- 教程受众层级：`1 / 2 / 3`
- 术语解释深度：需要解释到什么程度
- 是否必须先给完整案例
- 是否需要第二个完整案例做迁移
- 是否需要 Mermaid / 目录树 / 表格 / 伪输出示意

如果已经确认属于技术向，并且文章类型属于“教程型”，还要继续考虑：

- 是否需要目录树 / 模块职责表 / 调用链示意
- 是否需要命令行伪输出或关键代码片段
- 是否需要把工程权衡显式写进正文

受众层级规则见：

- [tutorial-audience-and-visuals](tutorial-audience-and-visuals.md)

### 2. 调研模板确认

必须先发送标准确认话术，等待用户确认默认模板或提供自定义模板。

未确认前：

- 不进入正式调研
- 不进入全文写作

### 3. 教程型任务的受众确认

如果文章类型属于“教程型”，且用户没有明确说清受众层级，必须在正式调研前补问：

- `1` 完全零基础
- `2` 用过一点但仍属小白
- `3` 已入门，想进阶到资深

如果用户已经说清楚，则直接写入任务卡，不重复追问。

### 4. 技术向任务的受众与主题确认

如果主题明显偏开发、工程、架构，而用户没有明确说清受众赛道，必须在正式调研前补问：

```text
这篇内容主要是写给通用 AI 使用者，还是写给程序员 / 技术人员 / 架构师？
```

如果已经确认属于技术向，任务卡里还应尽量明确：

- 是偏 vibe coding / AI 编程经验
- 还是偏 AI 开发工作流 / AI 工程
- 还是偏框架教程 / 源码解析 / 设计模式 / 架构设计

## 确认后的默认调研顺序

1. 先看官方文档
2. 再看官方仓库、官方博客、作者资料
3. 再看高质量第三方教程
4. 技术向任务要额外补源码、examples、tests、maintainer 解释
5. 教程型任务要额外补中文高质量资料
6. 最后看社区讨论

教程型任务里的高质量第三方资料，优先同时覆盖：

- 英文官方生态里的高质量博客、教程、仓库示例
- 知乎高质量回答或专栏
- 掘金高质量实战文章
- 阿里云开发者社区文章
- GitHub README / Issues / Discussions / Examples
- 国内高质量博主或社区作者的长文教程

如果当前环境可用，默认优先使用 `firecrawl` 做外部调研。

推荐工作流：

1. `firecrawl search`
2. `firecrawl scrape`
3. 需要站内定位时用 `firecrawl map`
4. 需要批量文档时用 `firecrawl crawl`

如果任务属于技术向，优先把搜索词写成：

- `产品名 + 能力名 + official docs`
- `产品名 + api reference`
- `产品名 + guide / tutorial / release notes`

不要默认把 `site:` 语法当作唯一检索方式。

调研抓回页面后，不要把整页原文直接塞进调研稿。

至少先做这几步裁剪：

1. 提取和当前文章目标直接相关的段落
2. 保留关键命令、关键参数、版本、限制条件
3. 去掉明显无关的导航、登录提示、验证码噪音和长段示例噪音
4. 再整理成结构化要点或事实核验表

调研完成后，先整理成调研稿或结构化要点，再进入正文撰写。

## 从 0 写作的输出顺序

1. 模式判断：从 0 撰写新稿
2. 文章类型判断
3. 任务卡
4. 调研稿或调研要点
5. 结构建议
6. 正式成稿

## 关键提醒

- 不要凭印象直接开写
- 先确定最值得写的角度，再组织材料
- 对时效性强的工具、版本、参数、命令，优先显式标注核验日期
- 教程型正文深度必须跟着受众层级走，不能把进阶稿写成小白稿，也不能把小白稿写成术语堆积
- 面向 `1` 或 `2` 时，优先使用“完整案例 → 拆术语 → 第二个案例”的结构
- 面向 `3` 时，可以优先写架构、取舍、边界、工程化和复杂踩坑
- 如果正文是教程型，必须明确交代最小闭环
- 如果受众赛道属于技术向，必须补版本、环境、依赖、兼容性、工程边界和替代方案
- 如果受众赛道属于技术向，调研时还要主动控制搜索词质量和页面去噪质量，不要把搜索工具输出直接当正文事实
