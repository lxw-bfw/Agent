# 工作流总览

## 目标

这套 SOP 不是普通润色流程，而是把任务升级为“付费级教程生产”。

固定目标包括：

1. 经过核验的正式正文
2. 资料来源清单
3. 版本与适用范围说明
4. 必要的误区纠偏与踩坑提醒

## 总流程

1. 先判断模式：改写 / 从 0
2. 模式不明确时先问用户
3. 如果主题偏开发、工程、架构，再判断受众赛道：通用向 / 技术向
4. 再判断文章类型：推荐型 / 教程型 / 方法论型
5. 如果属于“从 0 撰写 + 教程型”，受众层级不明确时先确认 `1 / 2 / 3`
6. 输出任务卡
7. 确认资料优先级和风格策略
8. 先出新结构，再进正文
9. 成稿强制补齐核验日期、误区、踩坑、边界、来源

## 资料优先级

1. 官方文档、官方仓库、官方博客、release note
2. 作者本人或维护者的一手表达
3. 高质量第三方教程
4. 社区讨论，仅作辅助

如果受众赛道属于“技术向”，资料优先级升级为：

1. 官方文档、API / SDK / CLI 参考、最佳实践、release note、migration guide、RFC
2. 官方 GitHub 仓库、examples、starter、demo、tests、fixtures、关键模块源码、ADR / design note
3. 作者本人、维护者、核心贡献者的一手表达
4. 高质量技术作者或架构师写作
5. 社区讨论，仅作翻车点和兼容性补充

如果当前环境可用，默认优先使用 `firecrawl` 完成网页调研：

1. `firecrawl search`
2. `firecrawl scrape`
3. 需要站内定位时用 `firecrawl map`
4. 需要批量文档时用 `firecrawl crawl`

如果文章类型属于“教程型”，第三方教程要尽量同时覆盖：

- 英文高质量资料
- 中文高质量资料，例如知乎、掘金、阿里云开发者社区、GitHub README / Issues / Discussions

## 对正文的最低要求

- 讲清楚这篇文章到底卖什么
- 对新手有明确学习顺序或执行路径
- 对容易过时的内容给出核验日期和边界
- 不是只复述资料，而是形成判断和重组
- 教程型内容要根据受众层级决定术语解释密度与案例组织方式
- 教程型内容要让读者知道如果只跑最小闭环，应该怎么做
- 适合可视化的地方，优先补 Mermaid 流程图、目录树、表格或伪输出示意

如果受众赛道属于“技术向”，还要继续满足：

- 讲清楚技术前提、版本范围、依赖和兼容性
- 解释为什么这样设计，而不只写“好不好用”
- 需要时补目录树、模块职责表、调用链、命令行伪输出或伪代码
- 源码解析 / 框架解析 / 设计模式类文章，事实判断继续以源码和官方文档为主
