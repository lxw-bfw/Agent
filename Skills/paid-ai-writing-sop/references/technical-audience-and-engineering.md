# 技术向受众与工程写作附加规则

## 适用条件

当任务明显属于下面这些方向时，优先使用这份规则：

- vibe coding 经验
- AI 编程工作流
- Agent engineering / context engineering / evals / observability
- AI 工程实践
- SDK / API / CLI / MCP / Agent 框架教程
- 源码解析
- 技术框架
- 设计模式
- 软件架构 / 系统拆解 / 模块设计

## 一、先判断是不是技术向任务

不是所有 AI 教程都该按“通用读者”来写。

如果主题明显偏开发、工程、架构，先判断受众赛道：

1. `通用向`：普通 AI 使用者、内容创作者、运营、产品初学者
2. `技术向`：程序员、技术人员、架构师、技术管理者、工程团队

如果用户没有明确说清，必须先问：

```text
这篇内容主要是写给通用 AI 使用者，还是写给程序员 / 技术人员 / 架构师？
```

如果已经确认属于技术向，并且文章类型还是“教程型”，后面仍然要继续走教程受众分层：

1. 完全零基础
2. 用过一点但仍属小白
3. 已入门，想进阶到资深

注意这里的“零基础”，是相对当前技术主题而言，不代表完全不懂电脑。

## 二、技术向任务必须再细分主题

至少补一层技术主题细分：

- `A` vibe coding / AI 编程经验
- `B` AI 开发工作流 / Agent 工作流
- `C` AI 工程实践：测试、评测、部署、监控、成本、稳定性
- `D` 框架 / SDK / 平台教程
- `E` 源码解析 / 调用链 / 关键模块拆解
- `F` 设计模式 / 架构设计 / 系统设计

没有这层细分，后面的资料优先级和正文骨架容易混乱。

## 三、技术权威参考和中文成稿风格要分层

### 技术判断参考层

负责：

- 事实准确性
- 工程判断
- 架构取舍
- 真实限制
- 安全、性能、成本、可维护性判断

默认优先参考：

- Simon Willison：LLM 实战、开发者工具、Agent 风险与工作流
- Chip Huyen：AI engineering、生产级系统、评测与架构
- Hamel Husain：LLM evals、应用 AI 工程、质量度量
- Andrej Karpathy：Software 3.0、vibe coding、AI 编程范式判断
- Martin Fowler / Thoughtworks 技术作者群：AI 辅助软件开发、agentic coding、架构抽象、工程边界
- 宝玉：软件工程、AI 编程、官方文档转译、规则型技术写作
- stormzhang：程序员 / 技术产品人视角下的 AI 工具、AI 编程与落地经验

### 中文成稿风格层

负责：

- 标题抓力
- 中文表达节奏
- 场景切入
- 教程推进体感
- 内容包装与可读性

可继续参考：

- 歸藏
- 宝玉
- 数字生命卡兹克
- 翔宇工作流
- stormzhang

### 当前默认作者的边界

- 歸藏：适合趋势判断、工具脉络、概念转译，不适合作为源码解析或架构细节的默认权威
- 宝玉：当前默认作者里最适合承接技术解释、软件工程和 AI 编程规则写法
- 数字生命卡兹克：适合标题、导语、产品化包装，不适合单独承担技术深水区判断
- 翔宇工作流：适合 AI 编程和工作流实操案例，不适合单独承担框架原理、源码设计或架构严谨性背书

结论：

- 风格作者可以继续做中文表达层参考
- 不能再默认替代技术事实与工程判断

## 四、技术向任务的资料优先级

默认按下面顺序走：

1. 官方文档、API / SDK / CLI 参考、最佳实践、release note、migration guide、RFC
2. 官方 GitHub 仓库、examples、starter、demo、tests、fixtures、关键模块源码、ADR / design note
3. 作者本人、维护者、核心贡献者的一手表达：博客、演讲、issue / discussion / RFC 回复、访谈 / AMA
4. 高质量技术作者或架构师写作：有代码、命令、版本、边界、取舍说明
5. 社区讨论，仅用于补翻车点、迁移痛点、兼容性问题和真实抱怨

### 官方检索关键词范式

为了更稳定地命中官方资料，技术向任务做网页搜索时，优先使用“产品名 + 能力名 + official docs / api reference / guide / github / release notes”这一类关键词。

例如：

- `OpenAI Responses API official docs`
- `FastAPI first steps official docs`
- `Firecrawl OpenAI integration docs`
- `LangGraph persistence docs`
- `Vercel AI SDK tool calling docs`

不建议默认把传统搜索引擎里的 `site:` 语法当作唯一检索方式。

原因：

- 某些搜索工具或聚合器对 `site:` 兼容性不稳定
- 直接写产品名、能力名和文档类型，往往更容易命中官方入口页
- 先找到官方入口页，再继续用站内定位、API 参考和仓库文件补细节，通常更稳

如果第一次没有命中官方文档，优先按下面顺序重试：

1. 把关键词改成“产品名 + 具体能力名 + official docs”
2. 再改成“产品名 + api reference / guide / tutorial”
3. 再补官方 GitHub 仓库名或官方维护者名
4. 最后再考虑 `site:` 作为辅助，而不是主入口

## 五、技术向任务的调研补充字段

除原来的任务卡与事实核验表外，还要补：

- 受众赛道：通用向 / 技术向
- 技术主题细分：A / B / C / D / E / F
- 目标技术栈：语言 / 框架 / 运行环境 / 部署方式
- 版本范围：文章基于哪些版本或日期
- 仓库范围：要看哪个 repo、哪个目录、哪些关键文件
- 最小闭环：最短跑通路径是什么
- 核心调用链：入口在哪里、关键模块怎么串
- 工程权衡：性能 / 成本 / 稳定性 / 安全 / 可维护性
- 替代方案：为什么不用另一种方案

如果主题属于源码解析或框架解析，还要补：

- 目录树
- 模块职责表
- 主调用链
- 关键抽象
- 关键设计取舍

## 六、技术向正文的附加表达部件

优先补这些东西：

- Mermaid 流程图
- Mermaid 时序图
- 目录树
- 模块职责表
- 输入 / 输出示意
- 命令行伪输出
- 关键代码片段或伪代码
- 最小可运行步骤

### 如果是源码解析 / 设计模式 / 框架类文章

优先按这个顺序组织：

1. 先给结论
2. 再给目录或模块地图
3. 再讲主调用链
4. 再拆关键抽象与设计模式
5. 再讲为什么这样设计
6. 再讲限制、边界和替代方案
7. 最后给可迁移经验

### 如果是 vibe coding / AI 开发工作流类文章

优先按这个顺序组织：

1. 先给真实结果或完整案例
2. 再交代工作流全貌
3. 再拆 prompt / context / tools / memory / evals / handoff
4. 再讲怎么验证做对了
5. 再讲最容易翻车的点
6. 再讲什么时候必须人工接管
7. 最后讲适用边界

## 七、技术向任务的硬约束

- 不允许只靠二手博客拼技术结论
- 不允许把风格作者当作技术权威替代源码和官方文档
- 不允许只讲“好不好用”，必须讲“为什么这样设计”
- 不允许只给 happy path，必须补失败路径、排错线索和边界
- 不允许把程序员文章写成纯情绪化工具种草文
- 不允许跳过版本、环境、依赖、权限、兼容性说明
- 不允许把抓回来的整页文档原样堆进调研稿，必须先裁剪出和正文目标最相关的段落、命令、版本和限制条件
