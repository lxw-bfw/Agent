# `paid-ai-writing-sop` 技能系统完整拆解

## 一、整体架构：一套「分流→约束→装配」管线

这个 Skill 本身不是一个 prompt，而是一套**工作流编排系统**。它的核心设计思想可以概括为三层：

```
SKILL.md          ← 入口：路由规则、硬约束、输出标准（司令员）
references/       ← 流程定义：每种模式的具体步骤和检查点（作战手册）
assets/           ← 提示骨架：内部复用的输出话术模板（战场指令卡）
```

> ★ 这套系统的关键设计是 **"约束驱动"而非 "prompt 驱动"**。普通的 AI 写作 skill 通常只给一个大 prompt 让 AI 直接写，但这个 SOP 通过多层路由、强制确认点、检查清单，确保 AI 不会跳过关键步骤——这是它和普通"帮我写一篇文章"的本质区别。

---

## 二、两条核心流水线对比

### 模式 A：改写已有原稿

**进入条件**：用户提供了原稿，或明确说「改写/重写/升级/润色」。

**完整流水线**：

```
[判断模式A] → [加载 workflow-overview] → [必要时判断通用向/技术向]
    → [判断文章类型]
    → [加载 rewrite-mode + style-strategy + article-templates + prompts-rewrite]
    → [输出任务卡（8项）]
    → [输出原稿问题清单]
    → [提取风格策略]
    → [输出新结构]
    → [用户确认后进入正式改写]
```

**关键机制——「任务卡」是质量锚点**：

rewrite-mode 要求改写前必须补齐的 8 项中，有三项是关键差异化：

| 任务卡项       | 作用                                             |
| -------------- | ------------------------------------------------ |
| **时效性**     | 哪些内容容易过期——这是付费文章和普通文章的分水岭 |
| **风险点**     | 哪些说法可能旧、错、空、泛——主动识别债务         |
| **可保留资产** | 原稿里哪些案例/结构/比喻值得留——不是全盘推翻     |

这套设计的精妙之处在于：它**不是简单润色，而是先诊断再手术**。「可保留资产」这个概念特别关键——它迫使 AI 在动手前先做价值判断，区分"要删的"和"要留的"，而不是无差别重写。

**改写原则的三条红线**：

1. **保核心信息，不保原结构**——允许推翻重建
2. **允许删除空段落、合并重复信息、前置关键结论**——信息密度优先
3. **优先补读者真正会卡住的步骤、判断和限制条件**——从读者视角回填

**改写时必须主动补的 5 类内容**：

- 版本变化导致的风险
- 常见误区和错误理解
- 上手路径或最小闭环
- 适合谁、不适合谁
- 资料来源清单

> ★ 这 5 项补内容正是普通免费教程和付费教程的**质量分水岭**。免费教程通常只讲"怎么做"，付费教程必须讲"什么时候不能这么做""谁不适合这么做""我这些东西是从哪来的"。SOP 通过硬约束把这些差异化内容变成了**必选项**，而不是可选项。

### 模式 B：从 0 撰写新稿

**进入条件**：用户只给了主题/背景/概要/平台/目标。

**完整流水线**：

```
[判断模式B] → [加载 workflow-overview] → [必要时判断通用向/技术向] → [判断文章类型]
    → [加载 research-confirmation]
    → [发送标准确认话术] → 🔒 阻塞，等待用户确认
    → [用户确认后]
    → [加载 from-zero-mode + research-template + style-strategy + article-templates + prompts-from-zero]
    → [输出任务卡（8项）]
    → [执行调研（四级资料优先级）]
    → [输出调研稿（14个模块）]
    → [输出结构建议]
    → [正式成稿]
```

**最关键的设计——调研确认门控**：

这是整个 SOP 中唯一的**强制阻塞点**。research-confirmation.md 定义了一个"行为契约"：

> 只有在以下两种情况下，才进入正式调研：
>
> 1. 用户提供了自己的调研模板
> 2. 用户明确回复"没问题，开始工作吧"

这个门控的意义：**阻止 AI 凭训练数据中的记忆直接开写**。对于时效性强的 AI 工具教程，凭记忆写几乎一定会出错（版本号、API 参数、界面截图都对不上）。这个阻塞点是质量保证的**第一道防线**。

**默认调研模板（research-template.md）的 14 模块设计逻辑**：

```
模块 1-2：定方向     ← 任务卡 + 初步判断（"这篇文章最值得写的角度"）
模块 3-4：定策略     ← 核心问题 + 资料搜集策略（四级优先级）
模块 5-6：定事实     ← 资料来源清单 + 事实核验表
模块 7-8：定内容     ← 关键结论（结论/误区/边界三层）+ 可直接用的案例
模块 9-10：定结构    ← 可视化表达计划 + 文章结构建议
模块 11-12：定写法   ← 参考写法 + 成稿底线 checklist
模块 13-14：定缺口   ← 信息缺口 + 下一步建议
```

> ★ 这 14 个模块之所以有效，是因为它们**按认知顺序排列**：先理解"我们要写什么"（1-2），再确认"我们怎么收集信息"（3-4），然后验证"我们收集到的信息对不对"（5-6），最后才进入"怎么组织和呈现"（7-10），并显式收口到写法底线与信息缺口（11-14）。这避免了 AI 写作中最常见的问题——先想好结构再去找资料，结果写出来的东西被结构框死，而不是被事实驱动。

**这次新增的两层门控：技术向确认 + 教程受众分层确认**

如果主题明显属于：

- AI 编程
- vibe coding
- AI 开发工作流
- AI 工程实践
- 技术框架
- 源码解析
- 设计模式

现在会先多判断一层：

1. 通用向
2. 技术向

如果确认属于技术向，Skill 会继续加载：

- `references/technical-audience-and-engineering.md`

然后才进入原来的文章类型判断与教程受众分层判断。

这层门控的意义，是防止把程序员文章按普通 AI 教程写法处理。

技术向确认之后，如果文章类型又是“教程型”，才继续进入下面这层：

在“从 0 撰写 + 教程型”任务里，现在还会再多一层专门的确认：

1. 完全零基础
2. 用过一点但仍属小白
3. 已入门，想进阶到资深

这层门控的意义，不是形式化补问，而是为了防止两种常见失败：

- 把零基础教程写成术语堆积稿
- 把进阶教程写成按钮说明书

也就是说，这套 SOP 现在不仅要判断“写不写教程”，还要进一步判断“这篇教程到底该用哪一种教学粒度”。

## 三、文章类型三分法：决定结构骨架

article-types.md 定义了三种文章类型，分流标准极其简洁：

| 类型     | 卖什么       | 核心问题                           | 结构锚点                     |
| -------- | ------------ | ---------------------------------- | ---------------------------- |
| 推荐型   | 知道该选什么 | 哪个值得选、适合谁、新手先走哪条路 | 结论前置 → 筛选标准 → 速查表 |
| 教程型   | 知道怎么做   | 怎么装、怎么配、怎么跑通           | 环境前提 → 最小闭环 → 排错   |
| 方法论型 | 知道怎么判断 | 为什么、怎么判断、常见误解         | 纠偏前置 → 判断框架 → 反例   |

这里有一个非常重要的设计决策：**如果一篇文章同时沾两类，优先按它最终售卖的主要价值判断，不按篇幅多少判断**。这避免了"教程里夹了一段推荐就变成推荐型"的分类漂移。

对于“教程型”，现在还要继续往下分一层：

- `1` 完全零基础
- `2` 用过一点但仍属小白
- `3` 已入门，想进阶到资深

其中 `1` 和 `2` 的默认写法，优先是：

1. 先给一个完整案例
2. 再借案例拆术语
3. 最后带读者做第二个完整案例

而 `3` 可以更偏向：

1. 先给结构图或结论
2. 再讲设计取舍
3. 再讲工程化、边界和复杂踩坑

## 四、风格策略：两层参考 + 红线约束

style-strategy.md 现在不是给一个笼统的"写作风格"，而是先拆成：

1. **技术判断参考层**
2. **中文成稿风格层**

对于中文成稿风格层，四类默认参考对象分别承担不同角色：

```
歸藏 → 主结构骨架    （开头先给判断、结构推进清楚、主动写边界和限制）
宝玉 → 解释层/教程层  （抽象内容拆步骤、一段话只讲一个判断、克制专业）
卡兹克 → 标题和导语   （开头抓力、场景切入、快速说明"对谁有用"）
翔宇工作流 → 实操与工作流表达（先展示结果，再拆模块和排错）
```

如果任务偏程序员 / 技术人员，Skill 还会额外参考一组技术判断对象：

- Simon Willison
- Chip Huyen
- Hamel Husain
- Andrej Karpathy
- Martin Fowler / Thoughtworks 技术作者群
- 宝玉
- stormzhang

这组人不是拿来模仿口头禅，而是拿来校准：

- 技术事实
- 工程判断
- 架构取舍
- 真实边界

同时定义了**4 条写法红线**和**付费层质感的 5 个来源**：

> 结构更像老师，而不是资料搬运工。会先替读者做选择和排序。会主动指出误区、边界、适用人群。会交代时效性和核验日期。

**4 条写法红线**：

- 不要写成"AI 整理稿"口吻
- 不要全篇堆链接、堆功能点
- 不要只说"很强、很方便、很值得"
- 不要回避限制条件和失败场景

除此之外，Skill 现在还补上了两层更显式的资产：

- `assets/style-extraction-template.md`
  负责把“参考谁的风格”拆成标题、开头、结构、术语解释、边界和结尾等可执行字段
- `assets/title-and-intro-patterns.md`
  负责给推荐型、教程型、方法论型任务补标题和第一屏开场骨架

## 五、硬约束系统：所有成稿必须补齐的 5 项

这是 SOP 中最体现"付费级"定义的部分。无论模式 A 还是模式 B，成稿结尾必须显式补齐：

| 必须补齐项       | 为什么重要                                           |
| ---------------- | ---------------------------------------------------- |
| **核验日期**     | 让读者判断信息是否已过期，这是对付费读者的责任       |
| **误区纠偏**     | 主动指出"你以为是这样，其实不是"——付费内容的核心价值 |
| **踩坑提醒**     | 把自己踩过的坑列出来，节省读者时间                   |
| **适用边界**     | 明确"什么场景下这篇文章不适用"——防止读者用错         |
| **资料来源清单** | 透明化信息来源，建立信任，也方便读者深挖             |

在这 5 项之外，交付前现在还建议统一过一遍：

- `references/review-checklist.md`

它补了两层之前主要停留在人类文档里的东西：

- `7 项质检`
- `5 项快速打分法`

## 六、两条流水线的本质差异总结

| 对比维度   | 模式 A（改写）      | 模式 B（从 0）          |
| ---------- | ------------------- | ----------------------- |
| 核心动作   | 诊断 → 手术         | 调研 → 构建             |
| 前置条件   | 用户提供原稿        | 用户提供主题            |
| 关键阻塞点 | 无（可立即开始）    | 调研确认门控            |
| 产出物差异 | 原稿问题清单        | 调研稿（14 模块）       |
| 风险重点   | 原稿信息过时 / 错误 | 凭记忆瞎写 / 信息不核验 |
| 保留策略   | 识别「可保留资产」  | 从零构建所有内容        |

## 七、核心设计哲学

> ★ 这套 SOP 最核心的设计哲学可以浓缩为一句话：**用流程约束替代对 AI 能力的信任**。它不假设 AI 会主动做调研、会主动标注核验日期、会主动区分推荐型和教程型——而是通过固定的检查点、阻塞门控、和必填模块，把这些"好的写作习惯"变成**不可跳过的流程步骤**。这就是它从"写一篇教程"升级为"生产付费级内容"的关键所在。

---

## 八、可复用的设计模式

1. **门控模式**：在容易跳过的关键步骤前设置显式确认点（如 research-confirmation），阻止 AI 凭惯性前进。
2. **角色分层模式**：不要求一个 prompt 同时做好结构、解释和导语，而是把不同写作层分配给不同风格的参考对象。
3. **底线 checklist 模式**：把付费内容的差异化要素（核验日期、边界、误区）从"建议"升级为"硬约束"，确保每篇成稿都达到同一质量标准。
4. **受众分层模式**：同样是教程型文章，先判断读者处于哪一层，再决定术语解释密度、案例组织方式和是否必须加入可视化示意。
5. **可视化兜底模式**：缺少真实截图时，优先用 Mermaid 流程图、目录树、表格、伪输出示意去补读者的理解缺口。
6. **技术向分流模式**：对程序员 / 技术人员内容，先判断是不是技术向，再把技术事实层和中文表达层拆开处理。
